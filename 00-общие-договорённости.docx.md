## **2\. Четыре поправки к схеме**

Схема в целом остаётся как есть, но эти четыре момента нужно учесть, иначе не выполним требования ТЗ.

1. **Горячий путь без синхронных внешних вызовов.** Цепочка «Frontend → Backend → ETL → внешние API → модель» на каждый запрос пользователя не уложится в p95 \< 300 мс. Поэтому:

   * ETL по расписанию или при старте забирает внешние данные и вызывает модель в пакетном режиме; прогнозы на день, месяц и год заранее сохраняются в БД.

   * Запрос пользователя читает готовые прогнозы из БД (через ETL, стрелки 4 → 7/8 → 12\) и применяет коэффициенты в бэкенде.

   * Модель вызывается онлайн только если прогноза в БД нет.

   * Если через ETL p95 всё равно не укладывается, добавляем на схему одну стрелку: Backend → БД сервиса (только чтение).

2. **Фронтенд не пишет логи в БД напрямую** (стрелка 15.x от Frontend). Браузер не может и не должен ходить в PostgreSQL. Логи и метрики фронта идут в бэкенд POST /api/v1/telemetry, бэкенд пишет их в базу логов.

3. **Корпоративного SSO на хакатоне нет.** Поднимаем Keycloak локально в Docker с готовым realm и демо-учётками для жюри. Без демо-логина жюри не попадёт в сервис.

4. **Внешние API нужны с историей.** Для обучения модели нужны данные за период датасета, а не только текущие. Каждый источник проверяем на наличие истории до того, как на него завязываться. На каждый источник обязательна рабочая ссылка в README, иначе балл по критерию 2а не засчитывается.

## **4\. Стандарты для всех сервисов**

### **4.1. Сквозной идентификатор запроса**

* Фронтенд генерирует X-Request-ID (UUID) на каждый запрос к API.

* Каждый сервис принимает заголовок, пробрасывает его дальше по цепочке и пишет в каждую строку лога.

* Если заголовка нет, сервис генерирует его сам.

Так в Grafana по одному request\_id видна вся цепочка запроса.

### **4.2. Логи**

Каждый сервис пишет логи в JSON в stdout и асинхронно пачками в базу логов через общий модуль из /common (пишет Вова). Запись лога не должна блокировать обработку запроса.

Поля записи:

| Поле | Пример |
| :---- | :---- |
| ts | 2026-09-27T12:00:00.123+03:00 |
| service | backend, etl, ml, frontend |
| level | DEBUG, INFO, WARNING, ERROR |
| request\_id | UUID |
| user\_id | из JWT, если есть |
| event | короткий код события: forecast\_served, etl\_stage\_done, external\_api\_error |
| message | текст |
| method, path, status, latency\_ms | для HTTP-запросов |
| payload | JSON с деталями |

### **4.3. Метрики**

Каждый Python-сервис отдаёт GET /metrics в формате Prometheus. Обязательный набор:

* http\_requests\_total{service, method, path, status};

* http\_request\_duration\_seconds{service, method, path} — гистограмма с бакетами 0.01, 0.025, 0.05, 0.1, 0.2, 0.3, 0.5, 1, 2, 5.

Специфичные метрики каждого сервиса описаны в его ТЗ. Имена начинаются с префикса сервиса: etl\_, ml\_, backend\_, frontend\_.

### **4.4. Проверки здоровья**

* GET /health/live — процесс жив.

* GET /health/ready — сервис готов: есть соединение с БД, модель загружена и т.п.

Используются в healthcheck docker-compose.

### **4.5. Формат ошибок API**

Один формат для всех сервисов:

{  
  "error": {  
    "code": "FORECAST\_NOT\_READY",  
    "message": "Прогноз для маршрута 17 на 01.10.2026 ещё не рассчитан. Повторите через минуту.",  
    "details": {"route\_id": "17", "date": "2026-10-01"},  
    "request\_id": "0b7c..."  
  }  
}

* message написан по-русски и понятен диспетчеру без знания системы.

* Коды HTTP: 400 (неверные параметры), 401, 403, 404, 422 (валидация), 503 (зависимость недоступна), 504 (таймаут).

### **4.6. Время и идентификаторы**

* В БД время хранится как timestamptz, на фронте отображается в Europe/Moscow.

* route\_id, stop\_id берутся из одного справочника, который ETL строит из датасета и сверяет с порталом открытых данных. Другие идентификаторы не придумываем.

* **Участок** — это диапазон подряд идущих остановок маршрута в одном направлении (route\_id, direction, from\_stop\_id, to\_stop\_id). Значение по участку — сумма значений по его остановкам. Если датасет позволяет оценить наполненность салона на перегоне, Артур и Марк договариваются об этом отдельно.

### **4.7. Горизонты и гранулярность**

| Горизонт | Гранулярность | Статус по ТЗ |
| :---- | :---- | :---- |
| day | час, 24 точки на день | обязательно |
| month | день | хотя бы качественно |
| year | месяц | хотя бы качественно |

### **4.8. Корректирующие коэффициенты**

* Коэффициенты: k\_weather, k\_event, k\_season, k\_traffic. Диапазон 0.5–1.5, по умолчанию 1.0.

* Формула: value\_adj \= value × k\_weather × k\_event × k\_season × k\_traffic.

* Применяет бэкенд к готовому прогнозу, модель не перезапускается. Поэтому пересчёт мгновенный.

* Значения пресетов («дождь», «праздник», «массовое мероприятие») Артур оценивает по данным. Бэкенд отдаёт их через GET /api/v1/factors.

## **5\. Контракты API (черновик, фиксируем до первой контрольной точки)**

Все сервисы на FastAPI автоматически публикуют OpenAPI по адресу /docs. Пока бэкенд не готов, фронтенд работает на моках по этим контрактам.

### **5.1. Публичное API бэкенда (Frontend → Backend, стрелки 3 и 13\)**

Все запросы с заголовком Authorization: Bearer \<JWT\>, кроме /health и /metrics.

| Метод и путь | Назначение |
| :---- | :---- |
| GET /api/v1/routes | список маршрутов |
| GET /api/v1/routes/{route\_id}/stops | остановки маршрута по порядку с координатами, по направлениям |
| GET /api/v1/routes/{route\_id}/geometry | GeoJSON линии маршрута для карты |
| GET /api/v1/forecast | прогноз по параметрам (см. ниже) |
| GET /api/v1/forecast/map | загрузка всех остановок на заданный час, для раскраски карты |
| GET /api/v1/forecast/export | те же параметры, что у /forecast, плюс format=csv|xlsx |
| GET /api/v1/factors | список внешних факторов: описание, ссылка на источник, пресеты коэффициентов |
| GET /api/v1/model/info | версия модели, WAPE, область применимости |
| POST /api/v1/telemetry | логи и метрики фронтенда |

Параметры GET /api/v1/forecast:

| Параметр | Обязательный | Пример |
| :---- | :---- | :---- |
| horizon | да | day, month, year |
| date\_from, date\_to | да | 2026-10-01 |
| route\_id | нет | 17 |
| stop\_id | нет | 1234 |
| segment\_from, segment\_to | нет | 1234, 1240 |
| time\_from, time\_to | нет | 07:00, 10:00 (интервал внутри суток) |
| group\_by | нет | route, stop, segment, none |
| k\_weather, k\_event, k\_season, k\_traffic | нет | 1.2 |

## **6\. Общая модель данных (детали схемы у Вовы)**

Сервисная БД:

* справочники: routes, stops, route\_stops (порядок остановок по направлениям), route\_geometry;

* исходные данные после нормализации: validations (партиционирование по месяцам), schedule, telematics;

* целевая величина: target\_hourly (route\_id, stop\_id, ts\_hour, passengers);

* внешние данные: ext\_weather\_hourly, ext\_traffic\_hourly, ext\_calendar\_days, ext\_events — у каждой записи источник и время загрузки;

* признаки для модели: features\_hourly;

* прогнозы: forecast\_runs (run\_id, model\_version, horizon, created\_at), forecasts (run\_id, horizon, ts, route\_id, stop\_id, value);

* агрегаты: материализованные представления по маршруту, остановке, дню и месяцу;

* метрики качества: model\_metrics (model\_version, horizon, route\_id, slice, wape);

* пользователи (если нужно сверх Keycloak): user\_scenarios — сохранённые наборы коэффициентов.

База логов: таблица logs с полями из раздела 4.2.
