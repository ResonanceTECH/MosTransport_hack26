# Правила работы в зоне DB и observability

Этот документ фиксирует безопасный порядок работы Вовы с базами данных, мониторингом и общей инфраструктурой проекта. Его цель — не затронуть рабочие копии и ветки других участников и заранее описывать точки стыковки компонентов.

## 1. Жёсткие границы рабочей зоны

- Рабочая копия на общей ВМ: `/home/aristarkhshavreev/MosTransport_hack26_db_observability`.
- Рабочая ветка: `db-observability-vova`.
- Любые изменения выполняются только при одновременном совпадении этой папки и этой ветки.
- Запрещено изменять, переименовывать, перемещать или удалять чужие рабочие копии, включая папки frontend, backend и ml.
- Запрещено переключаться на чужие ветки, создавать в них коммиты или отправлять в них изменения.
- Ветка `main` не изменяется напрямую. Создание PR и слияние в `main` выполняются только по отдельному явному решению команды.
- Если принадлежность файла или настройки неясна, работа останавливается до согласования с владельцем компонента.

## 3. Правила Git

- Коммиты разрешены только в ветке `db-observability-vova` и только из нашей рабочей копии.
- Перед коммитом проверить `git status`, затем `git diff` и `git diff --staged`.
- Добавлять файлы выборочно. Не использовать без проверки широкое `git add .`.
- Сообщение коммита должно кратко и точно описывать одно логическое изменение.
- `git push` выполняется только после явного разрешения Вовы для конкретной отправки.
- Допустимое направление push: только `origin/db-observability-vova`.
- Без отдельного явного разрешения запрещены `merge`, `rebase`, `cherry-pick`, `reset`, `clean`, force-push и изменение истории.
- Не использовать `git push --force` и `git push --force-with-lease` без отдельного разрешения.
- Не создавать PR и не выполнять merge в `main` без отдельного разрешения.
- Не исправлять чужие коммиты и не отправлять изменения от имени других участников.

Безопасная проверка перед разрешённым push:

```bash
git status
git diff --check
git log -1 --oneline
git push origin HEAD:db-observability-vova
```

## 4. Общая ВМ и общесерверные изменения

Общая ВМ используется всей командой. До изменения общей среды нужно согласовать действие и владельца.

К общесерверным изменениям относятся:

- установка, обновление и удаление пакетов;
- установка и настройка Docker, Compose, системных служб и демонов;
- изменение firewall, DNS, пользователей, групп, прав и системных конфигураций;
- создание cron-задач и фоновых процессов;
- публикация портов на хосте;
- изменение глобальных лимитов ресурсов, сетей и общих каталогов;
- остановка или перезапуск сервисов, которыми могут пользоваться другие участники.

Перед таким действием сообщить команде: что меняется, зачем, какие порты и сервисы затрагиваются, когда возможен простой и как выполнить откат.

## 8. Переменные окружения и секреты

- Реальные секреты хранятся только в локальном `.env` или в согласованном хранилище секретов.
- `.env` не коммитится. В репозитории хранится только `.env.example` без рабочих паролей, токенов и ключей.
- Не коммитить приватные ключи, сертификаты с закрытым ключом, API-токены, пароли, JWT, дампы с пользовательскими данными и файлы учётных данных.
- Не помещать секреты в README, команды запуска, логи, скриншоты, тестовые данные и историю Git.
- Для каждого параметра в `.env.example` указать назначение, допустимый формат и безопасное демонстрационное значение или пустую заглушку.
- Если секрет случайно попал в Git или лог, прекратить отправку, сообщить команде и заменить секрет; простого удаления строки недостаточно.

Минимальные группы переменных, которые следует документировать по мере реализации:

- подключение к сервисной БД и базе логов;
- отдельные учётные данные ETL, ML, backend, Grafana и writer логов;
- опубликованные порты Grafana, frontend и Keycloak;
- URL внутренних сервисов и targets Prometheus;

- демонстрационные учётные записи без реальных секретов.

## 9. Healthchecks и наблюдаемость

Для Python-сервисов общий контракт:

- `GET /health/live` — процесс запущен;
- `GET /health/ready` — сервис готов и необходимые зависимости доступны;
- `GET /metrics` — метрики в формате Prometheus.

Docker healthcheck должен проверять готовность, а зависимости в Compose — использовать `condition: service_healthy`, где это необходимо. Для PostgreSQL используется `pg_isready`. Healthcheck не должен требовать ручного входа и не должен раскрывать секреты.

Обязательные HTTP-метрики:

- `http_requests_total{service,method,path,status}`;
- `http_request_duration_seconds{service,method,path}`;
- специфичные метрики с префиксом сервиса: `backend_`, `etl_`, `ml_` или `frontend_`.

Логи пишутся в JSON в stdout и асинхронно пачками в базу логов. Отказ базы логов не должен останавливать обработку запросов. Во всех сервисах поддерживается `X-Request-ID`.

Команды ниже выполняются только после обязательной проверки папки, ветки и `git status`.

### Установка Docker на этой ВМ

На общей ВМ установлен Docker Engine 29.8.1, Docker Compose plugin 5.5.1 и Buildx 0.37.1 на Ubuntu 24.04 LTS x86_64. Установка выполнена из [официального apt-репозитория Docker для Ubuntu](https://docs.docker.com/engine/install/ubuntu/); системные пакеты и настройки репозитория относятся к общей ВМ, а не к Git-репозиторию.

Перед установкой или изменением Docker на общей ВМ требуется согласие команды. Установка добавляет официальный apt-репозиторий Docker, ключ подписи пакетов и пакеты Engine, CLI, containerd, Buildx и Compose plugin. Служба включена для автоматического запуска и активна. Проверка текущего состояния:

```bash

sudo docker buildx version
sudo systemctl is-active docker

```

Пользователь не добавлен в группу `docker`; выполняйте команды через `sudo`. Не меняйте членство в этой группе без отдельного согласования: доступ к сокету Docker даёт широкие системные привилегии. До публикации портов сверяйте их с командой и заносите утверждённые значения в Compose и README. ## 12. Стандарты документации и стыковки

Каждое изменение контракта сопровождается документацией в том же коммите. Документация должна отвечать на вопросы:

- где находится компонент и кто его владелец;
- как он запускается и проверяется;
- какие порты, сети, volumes и ресурсы использует;
- какие переменные окружения обязательны и где приведён безопасный пример;
- какие healthchecks и метрики предоставляет;
- какие API, таблицы, представления и форматы данных потребляет и отдаёт;
- как выполнить миграцию и безопасный откат;
- какие ограничения и известные проблемы существуют.

Имена сервисов, URL, поля, типы, часовой пояс и идентификаторы не придумываются локально. Используются согласованные контракты:

- время в БД — `timestamptz`, отображение — `Europe/Moscow`;
- сквозной идентификатор — `X-Request-ID` в запросах и `request_id` в логах;
- ошибки API — единый объект `error` с `code`, `message`, `details`, `request_id`;
- справочные `route_id` и `stop_id` приходят из единого набора данных;
- изменения схемы БД оформляются новой миграцией, а не ручным изменением рабочей базы.

Перед передачей изменения другому участнику указать: commit, затронутые файлы, новые переменные, миграции, порты, команды проверки и возможные несовместимости.

## 13. Критерии готовности изменения

Изменение готово к коммиту, если:

- проверены правильные папка и ветка;
- не изменены чужие каталоги и код без согласования;
- diff прочитан полностью и не содержит секретов;
- документация соответствует фактическим путям, портам и командам;
- конфигурация проходит доступные проверки;
- новые сервисы имеют healthcheck и описанные метрики;
- новые env-параметры добавлены в `.env.example`, а `.env` игнорируется;
- зафиксированы зависимости и интерфейсы с другими компонентами;
- разрушительные или общесерверные действия не выполнялись без разрешения.

После коммита push по-прежнему требует отдельного явного разрешения, кроме случая, когда такое разрешение уже дано для конкретного изменения в текущей задаче.

## 14. Цельные блоки работы

- Не передавать частичные правки как завершённый результат. Сначала собрать связанный и проверяемый блок целиком.
- Каждый завершённый блок включает изменение README либо явное объяснение, почему README менять не требуется.
- До коммита перечитать весь diff, выполнить `git diff --check` и доступные проверки, описать результат и ограничения.
- Коммитить только после этой проверки и только файлы нашей зоны.
- Push выполнять после отдельного явного разрешения на конкретную отправку и только в `origin/db-observability-vova`.
