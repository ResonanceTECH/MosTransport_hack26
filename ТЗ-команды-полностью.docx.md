## **2\. Четыре поправки к схеме**

Схема в целом остаётся как есть, но эти четыре момента нужно учесть, иначе не выполним требования ТЗ.

1. **Горячий путь без синхронных внешних вызовов.** Цепочка «Frontend → Backend → ETL → внешние API → модель» на каждый запрос пользователя не уложится в p95 \< 300 мс. Поэтому:

   * ETL по расписанию или при старте забирает внешние данные и вызывает модель в пакетном режиме; прогнозы на день, месяц и год заранее сохраняются в БД.

   * Запрос пользователя читает готовые прогнозы из БД (через ETL, стрелки 4 → 7/8 → 12\) и применяет коэффициенты в бэкенде.

   * Модель вызывается онлайн только если прогноза в БД нет.

   * Если через ETL p95 всё равно не укладывается, добавляем на схему одну стрелку: Backend → БД сервиса (только чтение).

2. **Фронтенд не пишет логи в БД напрямую** (стрелка 15.x от Frontend). Браузер не может и не должен ходить в PostgreSQL. Логи и метрики фронта идут в бэкенд POST /api/v1/telemetry, бэкенд пишет их в базу логов.

3. **Корпоративного SSO на хакатоне нет.** Поднимаем Keycloak локально в Docker с готовым realm и демо-учётками для жюри. Без демо-логина жюри не попадёт в сервис.

4. **Внешние API нужны с историей.** Для обучения модели нужны данные за период датасета, а не только текущие. Каждый источник проверяем на наличие истории до того, как на него завязываться. На каждый источник обязательна рабочая ссылка в README, иначе балл по критерию 2а не засчитывается.

## **4\. Стандарты для всех сервисов**

### **4.1. Сквозной идентификатор запроса**

* Фронтенд генерирует X-Request-ID (UUID) на каждый запрос к API.

* Каждый сервис принимает заголовок, пробрасывает его дальше по цепочке и пишет в каждую строку лога.

* Если заголовка нет, сервис генерирует его сам.

Так в Grafana по одному request\_id видна вся цепочка запроса.

### **4.2. Логи**

Каждый сервис пишет логи в JSON в stdout и асинхронно пачками в базу логов через общий модуль из /common (пишет Вова). Запись лога не должна блокировать обработку запроса.

Поля записи:

| Поле | Пример |
| :---- | :---- |
| ts | 2026-09-27T12:00:00.123+03:00 |
| service | backend, etl, ml, frontend |
| level | DEBUG, INFO, WARNING, ERROR |
| request\_id | UUID |
| user\_id | из JWT, если есть |
| event | короткий код события: forecast\_served, etl\_stage\_done, external\_api\_error |
| message | текст |
| method, path, status, latency\_ms | для HTTP-запросов |
| payload | JSON с деталями |

### **4.3. Метрики**

Каждый Python-сервис отдаёт GET /metrics в формате Prometheus. Обязательный набор:

* http\_requests\_total{service, method, path, status};

* http\_request\_duration\_seconds{service, method, path} — гистограмма с бакетами 0.01, 0.025, 0.05, 0.1, 0.2, 0.3, 0.5, 1, 2, 5.

Специфичные метрики каждого сервиса описаны в его ТЗ. Имена начинаются с префикса сервиса: etl\_, ml\_, backend\_, frontend\_.

### **4.4. Проверки здоровья**

* GET /health/live — процесс жив.

* GET /health/ready — сервис готов: есть соединение с БД, модель загружена и т.п.

Используются в healthcheck docker-compose.

### **4.5. Формат ошибок API**

Один формат для всех сервисов:

{  
  "error": {  
    "code": "FORECAST\_NOT\_READY",  
    "message": "Прогноз для маршрута 17 на 01.10.2026 ещё не рассчитан. Повторите через минуту.",  
    "details": {"route\_id": "17", "date": "2026-10-01"},  
    "request\_id": "0b7c..."  
  }  
}

* message написан по-русски и понятен диспетчеру без знания системы.

* Коды HTTP: 400 (неверные параметры), 401, 403, 404, 422 (валидация), 503 (зависимость недоступна), 504 (таймаут).

### **4.6. Время и идентификаторы**

* В БД время хранится как timestamptz, на фронте отображается в Europe/Moscow.

* route\_id, stop\_id берутся из одного справочника, который ETL строит из датасета и сверяет с порталом открытых данных. Другие идентификаторы не придумываем.

* **Участок** — это диапазон подряд идущих остановок маршрута в одном направлении (route\_id, direction, from\_stop\_id, to\_stop\_id). Значение по участку — сумма значений по его остановкам. Если датасет позволяет оценить наполненность салона на перегоне, Артур и Марк договариваются об этом отдельно.

### **4.7. Горизонты и гранулярность**

| Горизонт | Гранулярность | Статус по ТЗ |
| :---- | :---- | :---- |
| day | час, 24 точки на день | обязательно |
| month | день | хотя бы качественно |
| year | месяц | хотя бы качественно |

### **4.8. Корректирующие коэффициенты**

* Коэффициенты: k\_weather, k\_event, k\_season, k\_traffic. Диапазон 0.5–1.5, по умолчанию 1.0.

* Формула: value\_adj \= value × k\_weather × k\_event × k\_season × k\_traffic.

* Применяет бэкенд к готовому прогнозу, модель не перезапускается. Поэтому пересчёт мгновенный.

* Значения пресетов («дождь», «праздник», «массовое мероприятие») Артур оценивает по данным. Бэкенд отдаёт их через GET /api/v1/factors.

## **6\. Общая модель данных (детали схемы у Вовы)**

Сервисная БД:

* агрегаты: материализованные представления по маршруту, остановке, дню и месяцу;

* метрики качества: model\_metrics (model\_version, horizon, route\_id, slice, wape);

* пользователи (если нужно сверх Keycloak): user\_scenarios — сохранённые наборы коэффициентов.

### **4\. Фильтры и графики (P0)**

* Панель фильтров:

  * горизонт: день, месяц, год (для месяца и года пометка «оценочный прогноз»);

  * дата или период;

  * маршрут или несколько маршрутов;

  * остановка или участок;

  * интервал времени внутри суток, например 07:00–10:00;

  * группировка: по маршруту, по остановке, по участку.

* График динамики (ECharts или Recharts): линия прогноза и линия прогноза с коэффициентами. Если на историческом периоде есть факт — третья линия «факт».

* Тепловая карта «час × остановка» для выбранного маршрута: сразу видно пиковые часы и перегруженные остановки.

* Итоги над графиком: суммарный пассажиропоток за период, пиковый час, самая загруженная остановка.

* Фильтры хранятся в URL, чтобы ссылкой можно было поделиться и после перезагрузки всё осталось.

### **5\. Корректирующие коэффициенты (P0)**

Даёт балл по критерию 2в: пользователь меняет поправку и сразу видит, как меняется прогноз.

* Ползунки k\_weather, k\_event, k\_season, k\_traffic, диапазон 0.5–1.5, шаг 0.05, по умолчанию 1.0.

* Пресеты из GET /api/v1/factors: «дождь», «снегопад», «праздник», «массовое мероприятие». Нажатие выставляет ползунки.

* Пересчёт при движении ползунка с задержкой 200–300 мс: запрос /forecast с новыми коэффициентами, обновляются график, карта и итоги.

* Показ изменения: «+18% (+920 пассажиров) к базовому прогнозу».

* Кнопка «Сбросить».

* P2: сохранение набора коэффициентов как сценария (user\_scenarios), список сохранённых сценариев.

Критерий приёмки: движение ползунка обновляет график и карту менее чем за полсекунды.

### **6\. Выгрузка (P0)**

* Кнопки «Скачать CSV» и «Скачать XLSX» вызывают GET /api/v1/forecast/export с текущими фильтрами и коэффициентами.

* Имя файла включает маршрут, горизонт и дату.

* Индикатор загрузки на время формирования файла.

### **7\. Обработка ошибок (P0)**

Требование надёжности из ТЗ: понятные сообщения пользователю.

* Показывать error.message из ответа бэкенда, а не технический текст. Мелким шрифтом request\_id для поддержки.

* Отдельные состояния: загрузка (скелетоны), пустой результат («Для выбранных параметров нет данных»), нет сети, истёк токен (переход на вход).

* Кнопка «Повторить» при ошибке 503 и 504.

* ErrorBoundary на уровне страниц: падение одного графика не роняет всё приложение.

* Если в ответе meta.external\_data\_stale \= true, показывать плашку «Внешние данные устарели, прогноз может быть менее точным».

### **8\. Страница «О модели» (P1)**

Помогает по критерию 2: жюри видит источники и область применимости прямо в сервисе.

* Версия модели, дата обучения, WAPE по горизонтам из GET /api/v1/model/info.

* Список внешних источников со ссылками из GET /api/v1/factors.

* Текст об области применимости и ограничениях (текст даст Артур).

### **9\. Телеметрия: логи и метрики фронтенда (P1)**

* Сбор событий:

  * ошибки JavaScript (window.onerror, unhandledrejection, ErrorBoundary);

  * ошибки API (код, путь, request\_id);

  * длительность запросов к API;

  * Web Vitals (LCP, INP, CLS) через библиотеку web-vitals;

  * ключевые действия: смена маршрута, горизонта, коэффициентов, выгрузка.

* Отправка пачкой в POST /api/v1/telemetry раз в 10 секунд и при закрытии вкладки через navigator.sendBeacon.

Формат:

{  
  "events": \[  
    {"type": "error", "name": "api\_error", "ts": "...", "path": "/api/v1/forecast",  
     "status": 503, "request\_id": "...", "message": "..."},  
    {"type": "web\_vital", "name": "LCP", "value": 1830, "ts": "..."},  
    {"type": "action", "name": "coefficients\_changed", "ts": "...", "payload": {"k\_weather": 1.2}}  
  \]  
}

### **10\. Подготовка интеграций с БД (P0, до 08:00)**

Напрямую в БД фронтенд не ходит, но от тебя зависит, какие данные и в каком виде бэкенд и БД должны отдавать.

* Для каждого экрана выпиши, какие поля нужны и с какой агрегацией (карта, графики, тепловая карта, итоги, «О модели»). Отдай Марку и Вове. По этому списку Вова делает материализованные представления, а Марк — эндпоинты.

* Спецификация таблицы user\_scenarios (P2): id, user\_id (из токена Keycloak), name, коэффициенты, created\_at.

* Проверь, что справочники (маршруты, остановки, геометрия) отдаются одним запросом на маршрут, а не сотнями мелких.

### **11\. Контейнер и nginx (P0)**

* Многоэтапный Dockerfile: сборка на node:22-alpine, раздача статики через nginx:alpine.

* nginx:

  * раздаёт статику с кэшированием и gzip;

  * проксирует /api/ на backend:8000, чтобы у фронтенда и API был один адрес и не было проблем с CORS;

  * SPA-fallback на index.html.

* Адрес Keycloak и API задаются через переменные окружения при старте контейнера, а не при сборке.

* P2: stub\_status в nginx для nginx-prometheus-exporter (метрики настроит Вова).

## **Зона ответственности**

Блоки схемы:

* **Backend-модуль**: приём запросов фронтенда, проверка доступа, валидация, применение коэффициентов, выгрузки, телеметрия фронтенда.

* **ETL-модуль**: загрузка датасета, нормализация, геопривязка, внешние данные, подготовка данных для модели, оркестрация прогнозов, чтение прогнозов из БД.

Связи:

* фронтенд ↔ бэкенд (3, 13);

* бэкенд ↔ ETL (4, 12);

* ETL ↔ внешние API (5.x, 6.x);

* ETL ↔ БД сервиса (7, 8);

* ETL ↔ модель (9, 11);

* логи в базу логов (15.x), метрики для Prometheus (16.x).

Ключевое ограничение: запрос пользователя **не должен синхронно ходить во внешние API и в модель**. Прогнозы считаются заранее и лежат в БД, горячий путь только читает их (поправка 1 из общих договорённостей).

Приоритеты: **P0** — без этого не сдаём; **P1** — даёт баллы, делаем после P0; **P2** — если останется время.

## **Часть 1\. ETL**

### **1.1. Загрузка датасета (P0)**

* Скачать dataset.zip ([https://disk.yandex.ru/d/DiFwlfMOauxjBg](https://disk.yandex.ru/d/DiFwlfMOauxjBg)), изучить описание полей. Первым делом выписать, какие есть таблицы, поля, период, гранулярность, и поделиться с командой.

* Команда загрузки: docker compose run \--rm etl ingest и эндпоинт POST /etl/v1/ingest.

  * Идемпотентная: повторный запуск не создаёт дубликатов.

  * Быстрая загрузка в PostgreSQL через COPY, а не построчными INSERT.

  * Путь к архиву берётся из .env; архив не коммитим, в README пишем, куда положить.

* На каждом шаге писать в лог и метрики: сколько строк пришло, сколько отброшено и почему.

Критерий приёмки: с чистой БД одна команда загружает весь датасет; повторный запуск даёт тот же результат.

### **1.2. Нормализация и очистка (P0)**

* Приведение типов, единый часовой пояс (timestamptz, Europe/Moscow).

* Удаление дубликатов валидаций.

* Выбросы и некорректные записи: отрицательные значения, время вне работы транспорта, координаты вне Москвы. Правило, что с ними делаем, записать в README.

* Пропуски: явное правило для каждого поля (заполнить, отбросить или пометить).

* Единый справочник routes, stops, route\_stops (порядок остановок по направлениям) и route\_geometry. Сверить с порталом открытых данных Москвы.

### **1.3. Геопривязка (P0)**

Прямое требование ТЗ: геопривязка валидаций по расписанию и остановкам.

* Привязать каждую валидацию к маршруту, рейсу и остановке. Как именно, зависит от полей датасета. Типовой вариант:

  * если в валидации есть остановка — берём её;

  * если нет — берём координаты вагона из телематики на момент валидации и ищем ближайшую остановку маршрута в нужном направлении (буфер 50–100 м);

  * сверяем с расписанием: время валидации должно попадать в окно прохождения рейсом этой остановки.

* Доля непривязанных валидаций — отдельная метрика и строка в README.

* Участки строятся из route\_stops как диапазоны остановок (см. раздел 4.6 общих договорённостей).

### **1.4. Целевая величина (P0)**

* Таблица target\_hourly (route\_id, stop\_id, ts\_hour, passengers).

* **Агрегация должна совпадать с тем, что оценивается в сабмите Data Science.** Сверить с Артуром по описанию датасета и примеру сабмита до того, как считать.

* Проверка: сумма по target\_hourly за день равна числу привязанных валидаций за день.

За корректную агрегацию целевой величины и воспроизводимый пайплайн даётся балл по критерию 2в.

### **1.5. Внешние данные (P0 для календаря и погоды, P1 для трафика и событий)**

По критерию 2а за каждый источник 1 балл, но только если есть **рабочая ссылка или способ получения** и Артур подтвердил эффект.

* Для каждого источника **сначала проверить, есть ли история за период датасета**. Для обучения нужны прошлые данные, текущие и прогнозные не подходят.

* Источники по схеме:

| Источник на схеме | Что берём | Что проверить |
| :---- | :---- | :---- |
| Производственный календарь | выходные, праздники, переносы, сокращённые дни; школьные каникулы добавить отдельно | подойдёт любой открытый источник с API или файлом, например на портале открытых данных |
| Яндекс Погода | температура, осадки, снег, ветер по часам | API требует ключ и может быть платным; даёт ли историю за период датасета. Если нет — для обучения взять открытый архив погоды (например, Open-Meteo Historical), Яндекс оставить для прогноза на будущие дни |
| Яндекс Карты (пробки) | загруженность улиц по часам | есть ли доступ к истории пробок. Если нет — честно описать в README, что источник используется только для текущей ситуации, либо найти другой источник |
| Портал открытых данных Москвы | справочник остановок и маршрутов; перекрытия, ремонты, мероприятия | нужен API-ключ портала |

* Каждый источник описать в etl/sources.yaml: название, ссылка, способ получения, имя переменной с ключом, период, частота обновления. Этот файл — основа для раздела README со ссылками.

* Загрузка в таблицы ext\_weather\_hourly, ext\_traffic\_hourly, ext\_calendar\_days, ext\_events с полями source и fetched\_at.

* Недоступность внешнего API не роняет ETL: повтор с паузой, затем последние известные значения, в ответах meta.external\_data\_stale \= true.

* Ключи только в .env.

### **1.6. Данные для модели (P0)**

* Таблица features\_hourly: целевая величина, соединённая с календарём, погодой, трафиком и событиями по ts\_hour (и по району или остановке, если данные пространственные).

* Лаги и скользящие средние считает Артур у себя. Ты отдаёшь чистую соединённую таблицу без утечек из будущего.

* Экспорт в Parquet для обучения: docker compose run \--rm etl export-features.

### **1.7. Оркестрация прогнозов (P0)**

* POST /etl/v1/forecast/precompute: подготовить признаки на будущие даты и вызвать POST /ml/v1/predict/batch для горизонтов день, месяц и год по всем маршрутам и остановкам. Модель сама пишет результат в БД (стрелка 10).

* Запуск при старте стека, если прогнозов на ближайшие даты нет, и по расписанию (например, раз в час внутри процесса ETL; отдельный планировщик не нужен).

* После пакетного прогноза вызвать SQL-функцию обновления материализованных представлений (её делает Вова).

### **1.8. Чтение прогнозов (горячий путь, P0)**

* GET /etl/v1/forecast и GET /etl/v1/forecast/map читают из материализованных представлений и таблицы forecasts одним SQL-запросом.

* Пул соединений asyncpg; никаких внешних вызовов и вызовов модели в этом пути.

* Если прогноза нет: один онлайн-вызов POST /ml/v1/predict с таймаутом 2 секунды; если не успели — 503 с кодом FORECAST\_NOT\_READY и понятным сообщением.

* Справочники GET /etl/v1/reference/... — одним запросом на маршрут.

### **1.9. Приём потоковых данных (P2)**

В требованиях к производительности упомянут приём потоковых данных.

* POST /etl/v1/validations/stream: пачка валидаций в JSON, быстрая валидация, запись через COPY, ответ 202.

* Метрика принятых записей в секунду; замер попадает в README.

### **1.10. Логи и метрики ETL (P0)**

* Логи через общий модуль Вовы: начало и конец каждого шага, число строк, ошибки внешних API.

* Метрики:

  * etl\_rows\_processed\_total{stage, result} — result: ok, dropped;

  * etl\_stage\_duration\_seconds{stage};

  * etl\_external\_requests\_total{source, status};

  * etl\_external\_data\_age\_seconds{source} — насколько устарели внешние данные;

  * etl\_unmatched\_validations\_ratio — доля непривязанных валидаций.

## **Часть 2\. Бэкенд**

### **2.1. Каркас (P0)**

* FastAPI, асинхронный, запуск uvicorn с числом воркеров по числу vCPU (переменная окружения).

* orjson для ответов, pydantic для валидации параметров.

* Клиент к ETL — один httpx.AsyncClient с пулом соединений и таймаутами (подключение 0.5 с, чтение 2 с).

* Middleware: X-Request-ID (принять или сгенерировать, пробросить в ETL, вернуть в ответе), замер времени, лог каждого запроса.

* Конфигурация только через переменные окружения.

* **Сервис не хранит состояние**: никаких сессий в памяти, пользователь определяется только по JWT. Это требование горизонтального масштабирования. Небольшой кэш ответов в памяти процесса допустим, потому что при потере он просто пересобирается.

### **2.2. Аутентификация (P0)**

* Проверка JWT по ключам Keycloak (JWKS загружается при старте и кэшируется).

* Роли из токена: dispatcher — чтение и выгрузка, admin — плюс запуск пересчёта.

* Без токена — 401, без роли — 403, оба с понятным сообщением.

* Запасной план по договорённости с Дашей: POST /api/v1/auth/login с демо-учётками и выдачей JWT, если Keycloak не заведётся до 09:30.

### **2.3. Эндпоинты (P0)**

Контракты в разделе 5.1 общих договорённостей.

* GET /api/v1/routes, /routes/{id}/stops, /routes/{id}/geometry — проксирование справочников ETL с кэшем на 10 минут.

* GET /api/v1/forecast — валидация параметров → запрос в ETL → применение коэффициентов → ответ с value и value\_adj, итогами и meta.

* GET /api/v1/forecast/map — то же для раскраски карты.

* GET /api/v1/factors — факторы, ссылки на источники (из sources.yaml), пресеты коэффициентов (от Артура).

* GET /api/v1/model/info — проксирование /ml/v1/model/info.

* POST /api/v1/admin/recompute (только admin) — запуск POST /etl/v1/forecast/precompute.

Проверки параметров:

* date\_from ≤ date\_to;

* максимальная длина периода: day — 31 день, month — 12 месяцев, year — 3 года;

* segment\_from и segment\_to принадлежат одному маршруту и направлению.

Ошибки в формате из раздела 4.5, сообщения по-русски, например: «Период прогноза на день не может превышать 31 день. Сократите период или выберите горизонт "месяц"».

### **2.4. Корректирующие коэффициенты (P0)**

## **Задачи**

### **1\. Разобраться с оценкой (P0, первым делом)**

* По описанию в dataset.zip выяснить, **что именно оценивается в разделе Data Science**: какой горизонт, какая гранулярность (час, день, остановка, маршрут), какой период, формат CSV. Модель под сабмит важнее всего остального.

* Реализовать метрику точно по формуле из ТЗ:

**def** wape\_score(y\_true, y\_pred):  
    **return** max(0.0, 1.0 \- np.abs(y\_true \- y\_pred).sum() / y\_true.sum())

* Лимиты сабмитов в день: 36 попыток всего, 24 успешных. Вести таблицу сабмитов: время, версия модели, локальный WAPE, WAPE на платформе. Это же пригодится для README.

### **2\. Baseline и первый сабмит (P0, до 11:00)**

* Сезонный наивный прогноз: значение в тот же час того же дня недели неделю назад (или среднее за несколько недель).

* Посчитать локальный WAPE-score на отложенном периоде и сравнить с порогом 0.48.

* Отправить первый сабмит, чтобы убедиться, что формат принимается.

### **3\. Схема валидации (P0)**

* Разбиение только по времени: последние недели — отложенная выборка, без перемешивания.

* Бэктест со скользящим началом (3–4 окна), чтобы оценка не зависела от одной недели.

* Отложенный период по возможности похож на тот, что оценивается в сабмите (дни недели, праздники).

* Проверка на утечки: признаки не используют данные позже момента прогноза.

### **4\. Модель на день по часам (P0)**

* LightGBM, одна общая модель на все маршруты и остановки.

* Функция потерь objective="l1": WAPE — это сумма абсолютных ошибок, делённая на сумму факта, поэтому L1 оптимизирует ровно то, что оценивают. Для сравнения попробовать tweedie (хорошо подходит для счётных величин с нулями).

* Признаки:

  * идентификаторы: маршрут, остановка, направление, порядковый номер остановки (как категориальные);

  * время: час, день недели, выходной или будний, праздник, предпраздничный день, каникулы, месяц;

  * лаги с учётом горизонта: для прогноза на день — не ближе 24 часов (тот же час вчера, неделю назад, две недели назад), скользящие средние за 7 и 28 дней;

  * профиль остановки: среднее по этому часу и дню недели за историю;

  * внешние: температура, осадки, снег, пробки, события.

* Подбор гиперпараметров — короткий, в пределах часа. Качество больше зависит от признаков и чистоты данных.

* Прогноз не может быть отрицательным: обрезать снизу нулём.

Цель: WAPE-score выше 0.80 (8 баллов), в идеале выше 0.88 (10 баллов).

### **5\. Модели на месяц и год (P1)**

По ТЗ месяц и год достаточно «хотя бы качественно».

* **Месяц** — прогноз по дням: суточные суммы, признаки календаря и климатической нормы погоды, лаги не ближе 28–35 дней, значение год назад, если данных достаточно.

* **Год** — прогноз по месяцам: сезонный профиль по месяцам, умноженный на тренд. Честно пометить как оценочный.

* Для каждого горизонта свой WAPE на бэктесте, записать в model\_metrics.

* Если данных за год нет, в описании прямо написать, на чём основан годовой прогноз и почему он оценочный.

## **Задачи**

### **1\. Docker Compose (P0, до 08:00)**

* Один docker-compose.yml в корне со всеми сервисами: frontend, keycloak, backend, etl, ml, db, logs-db, prometheus, grafana, экспортеры.

* Для каждого сервиса: healthcheck, depends\_on с condition: service\_healthy, restart: unless-stopped.

* **Лимиты ресурсов** для бэкенда по ТЗ: cpus: "2", memory: 2g, memswap\_limit: 2g (swap запрещён). Для остальных — разумные лимиты, чтобы стек поднимался на ноутбуке жюри.

* Наружу открыты только фронтенд, Grafana и Keycloak; БД, ETL и модель — только во внутренней сети.

* Тома для данных PostgreSQL, Prometheus и Grafana.

* .env.example со всеми переменными и безопасными значениями по умолчанию; реальные ключи внешних API не коммитим.

* Проверка: git clone → cp .env.example .env → docker compose up \-d поднимает всё без ручных шагов.

Базы на схеме нарисованы отдельно. Можно поднять два контейнера PostgreSQL, а можно один контейнер с двумя базами transport и logs — это экономит память. Логически это всё равно две базы, как на схеме.

### **2\. Сервисная БД (P0, до 08:00 черновик, до 11:00 полностью)**

* PostgreSQL 16, миграции SQL-файлами в /infra/db/service/ с автоматическим применением при старте (docker-entrypoint-initdb.d или отдельный контейнер-мигратор).

* Таблицы из раздела 6 общих договорённостей:

  * справочники: routes, stops, route\_stops, route\_geometry;

  * исходные данные: validations (партиционирование по месяцам), schedule, telematics;

  * target\_hourly, features\_hourly;

  * внешние данные: ext\_weather\_hourly, ext\_traffic\_hourly, ext\_calendar\_days, ext\_events с полями source, fetched\_at;

  * прогнозы: forecast\_runs, forecasts;

  * model\_metrics;

  * P2: user\_scenarios по спецификации Даши.

* Индексы под горячие запросы: forecasts (horizon, route\_id, ts), forecasts (horizon, stop\_id, ts), target\_hourly (route\_id, stop\_id, ts\_hour).

* Роли доступа по принципу минимальных прав:

  * etl\_rw — запись исходных данных, внешних данных, признаков; чтение прогнозов;

  * ml\_rw — чтение признаков, запись прогнозов и метрик модели;

  * grafana\_ro — только чтение;

  * P1, если понадобится прямое чтение бэкендом: backend\_ro.

* Настройки PostgreSQL под ограниченную память: shared\_buffers, work\_mem, effective\_cache\_size, max\_connections — прописать в конфиге и объяснить в README одной строкой.

### **3\. Быстрая агрегация (P0, до 13:00)**

На твоём холсте это «функции быстрой агрегации данных». От них зависит p95 горячего пути.

* Материализованные представления по списку данных от Даши:

  * mv\_forecast\_route\_hour — прогноз по маршруту и часу;

  * mv\_forecast\_stop\_hour — по остановке и часу;

  * mv\_forecast\_route\_day, mv\_forecast\_route\_month — для горизонтов месяц и год;

  * mv\_forecast\_map\_hour — загрузка всех остановок на каждый час, для раскраски карты.

* SQL-функция refresh\_forecast\_views() с REFRESH MATERIALIZED VIEW CONCURRENTLY (нужны уникальные индексы). Её вызывает ETL после пакетного прогноза.

* Функция агрегации по участку: сумма по остановкам маршрута между from\_stop и to\_stop в заданном направлении.

* Проверить EXPLAIN ANALYZE на типовых запросах: цель — меньше 50 мс на запрос в БД.

### **4\. База логов (P0, до 10:00)**

* Таблица logs с полями из раздела 4.2 общих договорённостей; payload типа jsonb.

* Индексы: (ts), (service, ts), (request\_id), (level, ts).

* Хранение: партиционирование по дням или удаление записей старше 7 дней по расписанию.

* Отдельные роли: logs\_writer (только INSERT), grafana\_ro (только чтение).

### **5\. Общий модуль логирования и метрик (P0, до 10:00)**

Нужен, чтобы Марк и Артур не писали одно и то же трижды.

* Python-пакет в /common, подключается в backend, etl, ml:

  * настройка JSON-логов в stdout;

  * асинхронная запись в базу логов через очередь пачками (раз в секунду или по 100 записей); при недоступности базы логов сервис продолжает работать и пишет только в stdout;

  * middleware для FastAPI: X-Request-ID, замер времени, лог запроса, стандартные HTTP-метрики из раздела 4.3;

  * эндпоинты /metrics, /health/live.

* Короткая инструкция подключения в common/README.md (3–5 строк кода).

### **6\. Prometheus (P0)**

* prometheus.yml в /infra/prometheus/, сбор раз в 5–15 секунд:

  * backend, etl, ml — /metrics;

  * postgres\_exporter для обеих баз;

  * cAdvisor — CPU, память и swap по контейнерам (нужно для подтверждения требований ТЗ по ресурсам);

  * P2: nginx-prometheus-exporter для фронтенда.

* Правила записи: p50, p95, p99 задержки и RPS по сервисам и эндпоинтам, доля ошибок.

* Правила алертов:

  * p95 горячего пути больше 300 мс в течение 5 минут;

  * доля ошибок 5xx больше 1%;

  * CPU контейнера бэкенда больше 80%;

  * использование swap больше нуля;

  * сервис недоступен;

  * внешние данные устарели больше чем на сутки (etl\_external\_data\_age\_seconds);

  * пакетный прогноз не выполнялся больше 2 часов (ml\_batch\_last\_success\_timestamp).

На macOS в Docker Desktop cAdvisor показывает не все метрики. Если так вышло, для замеров в README используй docker stats и приложи вывод.

### **7\. Grafana (P0 дашборды, P2 SSO)**

* Источники данных и дашборды **задаются файлами** в /infra/grafana/provisioning/, а не вручную через интерфейс. Иначе у жюри после docker compose up Grafana будет пустой.

* Источники: Prometheus, PostgreSQL (база логов), PostgreSQL (сервисная БД, роль grafana\_ro).

* Дашборды:

  1. **Сервисы** — RPS, p50/p95/p99, доля ошибок по сервисам и эндпоинтам; линия порога 300 мс.

  2. **Ресурсы** — CPU, память, swap, перезапуски по контейнерам; линии лимитов 2 vCPU и 2 ГБ для бэкенда.

  3. **Данные и ETL** — строки по шагам пайплайна, доля непривязанных валидаций, свежесть внешних данных, ошибки внешних API.

  4. **Качество модели** — WAPE по горизонтам, маршрутам и часам из model\_metrics; время последнего пакетного прогноза; длительность прогноза.

  5. **Аналитика загрузки** — топ перегруженных остановок и часов по прогнозу, суммарный пассажиропоток по маршрутам. Этот дашборд пригодится на питче как пример бизнес-применения.

  6. **Логи** — таблица с фильтрами по сервису, уровню и request\_id; число ошибок по сервисам во времени; телеметрия фронтенда (ошибки, Web Vitals).

* Вход: P0 — логин и пароль администратора из .env, анонимный доступ выключен. P2 — вход через Keycloak (generic\_oauth) с клиентом из realm Даши, как на схеме (стрелки 17, 21).

### **8\. Нагрузочный тест (P0, 17:00–19:00)**

* Сценарий k6 в /infra/loadtest/, запуск одной командой, например docker compose run \--rm k6 run /scripts/forecast.js.

* Смесь запросов по описанию от Марка, примерно:

  * 70% — GET /api/v1/forecast (маршрут, день, по часам, со случайными коэффициентами);

  * 20% — GET /api/v1/forecast/map;

  * 10% — справочники.

  * Выгрузку тестировать отдельно: это тяжёлая операция с другими ожиданиями по времени.

* Токен для теста получать заранее от Keycloak под демо-учёткой.

* Профиль нагрузки: плавный рост от 50 до 500 RPS за 5 минут, затем удержание на максимальном уровне, при котором p95 меньше 300 мс.

* Бэкенд в тесте с лимитами из ТЗ: 2 vCPU, 2 ГБ.

* Во время теста снять с дашбордов Grafana: RPS, p95, CPU, память, swap. Скриншоты сохранить в /docs/perf/.

* P1: повторить при docker compose up \--scale backend=2 и показать рост пропускной способности — подтверждение горизонтального масштабирования.

## **Критерии готовности**

* Весь стек поднимается одной командой с чистого клона, все проверки здоровья зелёные.

* Миграции применяются автоматически; роли разграничены.

* Типовые запросы горячего пути выполняются в БД быстрее 50 мс.

* Логи всех сервисов, включая фронтенд, видны в Grafana и ищутся по request\_id.

* Шесть дашбордов подгружаются автоматически при старте Grafana.

* Нагрузочный тест проведён, таблица и скриншоты в README.
